## Modeling Implications

Initial recommendation:

1. Build a hierarchy-aware baseline at SKU/day or SKU/week.
2. Use historical sales as the primary demand signal.
3. Add promotion flags at date and offer/category level.
4. Add product lifecycle and hierarchy fields.
5. Use current plus expected inventory as a supply/availability cap and as a
   feature for launch/back-in-stock behavior, not as a naive demand driver.
6. Reconcile SKU forecasts back to corporate total units when corporate total
   demand is directionally reliable but SKU allocation is weak.

Backtest first:

- Train on historical sales before the evaluation month.
- Forecast the last complete month.
- Compare against actual sales.
- Compare against the corporate forecast snapshot that would have been available
  at that time.
- Measure both unit accuracy and SKU coverage.

Important metrics:

- WAPE by total and hierarchy.
- SKU coverage of sold units.
- Zero-forecast sold-unit percentage.
- Bias/net error.
- Promo-period versus non-promo-period error.
- New/lifecycle SKU error separately from replenishment SKU error.

### WAPE Interpretation

WAPE means weighted absolute percentage error:

```text
WAPE = sum(abs(forecast units - actual units)) / sum(actual units)
```

For this project, WAPE answers: across the full evaluation window, how many
absolute unit misses did the forecast create compared with the number of units
that actually sold or were fulfilled?

Example: if actual demand is `100,000` units and absolute forecast misses add
up to `42,000` units across all SKU/day rows, WAPE is `42%`.

WAPE is useful here because it is unit-weighted, so high-volume SKUs matter more
than tiny one-off misses. It also does not allow over-forecasting one SKU to
cancel under-forecasting another SKU. Both mistakes can hurt warehouse
operations: over-forecasting can waste active slots or drive unnecessary
replenishment, while under-forecasting can leave demand under-slotted and create
missed or late replenishment pressure.

Lower WAPE is better, but it should be read with bias and coverage:

- WAPE shows the total absolute size of the misses.
- Bias shows whether the forecast is systematically high or low.
- Coverage shows whether the model is missing sold SKUs entirely.

For slotting and replenishment, WAPE is the first scoreboard because the
warehouse feels unit misses, not just percentage misses. Bias then tells us
whether to calibrate up or down, and hierarchy/promo breakdowns tell us where
the model is failing.

## Candidate Model Test Matrix

The first ML runner uses scikit-learn `HistGradientBoostingRegressor`. That is a
good portable benchmark, but it should not be the last model tested. The goal is
not to chase the fanciest model; it is to prove which approach gives stable,
explainable SKU/day accuracy under promotion, seasonal, launch, and stockout
conditions.

Recommended next tests:

| Candidate | Why test it | Dependency impact |
|---|---|---|
| Regularized linear / Elastic Net on transformed features | Simple baseline that exposes whether tree complexity is really adding value. Useful for fast rolling-origin validation. | Already available in `scikit-learn`. |
| Random forest or extra trees | Nonlinear benchmark with different error behavior from histogram boosting. May be slower and larger. | Already available in `scikit-learn`. |
| Poisson / Tweedie gradient boosting | Unit demand is nonnegative and sparse; count-oriented losses may improve low-volume SKU behavior. | Already available in `scikit-learn` for Poisson-style tree boosting. |
| Quantile gradient boosting | Produces low/base/high demand bands instead of only one point forecast, useful for replenishment risk buffers. | Already available in `scikit-learn` via quantile loss support, depending on estimator choice. |
| LightGBM | Strong tabular forecasting candidate, handles large feature sets efficiently, often improves over scikit-learn boosting. | New dependency: `lightgbm`. Requires install/build validation on Windows. |
| XGBoost | Another strong tabular booster with mature regularization and feature-importance tooling. Good challenger to LightGBM. | New dependency: `xgboost`. Usually installs cleanly from wheels. |
| CatBoost | Handles categorical variables naturally and may reduce category-encoding friction for hierarchy and promo labels. | New dependency: `catboost`. Larger package; validate Windows install and runtime. |
| Two-stage demand model | First classify whether SKU/day demand occurs, then regress units when demand is positive. Useful for sparse SKU/day panels. | Can start with `scikit-learn`; optional booster dependencies later. |
| Hierarchical reconciliation model | Forecast at SKU/day but reconcile to item/category/day or corporate total constraints when aggregate signal is more reliable. | Mostly custom code plus current dependencies; may later use optimization libraries. |
| Rolling-origin ensemble | Combine recent-demand baseline, raw ML, calibrated ML, and possibly corporate aggregate signal based on window performance. | Can start with current dependencies. |

Testing discipline:

- Keep the current recent 7-day and recent 28-day baselines in every comparison.
- Report WAPE, bias, zero-forecast sold-unit percentage, and sold-unit coverage.
- Break results out by hierarchy, promo flag, lifecycle/newness, and velocity
  tier before calling a model better.
- Use rolling-origin windows, not a single lucky holdout.
- Track training time, model size, and required dependencies. A model that is
  slightly more accurate but hard to deploy on the shared PC may not be the best
  operational choice.

Dependency posture:

- Current dependencies are enough to test the next scikit-learn baselines,
  count-style losses, two-stage modeling, calibration variants, and rolling
  validation automation.
- Add external gradient boosting libraries one at a time, starting with
  `xgboost` or `lightgbm`, only after the scikit-learn matrix is repeatable.
- If a dependency is added, record its install command, Windows behavior, model
  runtime, and whether it works through `uv run` on the shared operations PC.
